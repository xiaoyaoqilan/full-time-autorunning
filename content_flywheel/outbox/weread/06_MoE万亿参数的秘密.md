# 06 · MoE：万亿参数为什么只激活一小撮

## 一句话

MoE（混合专家）的赌注：**容量和计算解耦**——参数管"知识存多少"，激活参数管"每次算多少"。DeepSeek-V3 总参 671B、每 token 只激活 37B，就是这个赌注的当代答案。

---

## 一、问题：稠密模型的暴力美学

稠密 Transformer（GPT 类）每个 token 都要过全部参数——知识全存在权重里，用一次付一次全款。代价：
- 训练算力 ∝ 参数量；
- 推理显存和带宽 ∝ 参数量；
- 想加知识就得加参数，加参数就得全款。

**MoE 的洞察：不同 token 需要的知识不同**。"写 Python"和"写法语诗"不需要同一批权重。把 FFN 层替换成 N 个并行的"专家"FFN，由路由器（Router）给每个 token 挑少数几个专家——这就是混合专家。

## 二、机制解剖

**路由**：对每个 token，Router（一个线性层 + softmax）打出 N 个专家的分数，取 top-k（通常 k=1~8）激活：

```
y = Σ_{i∈TopK(x)} g_i(x) · Expert_i(x)     # g_i 是路由权重
```

**稀疏账本**：总参 = N × 专家大小 × 层数，激活 = k × 专家大小 × 层数。k/N 可以压到 1/8 甚至更低——**这就是"万亿参数、千亿激活"的来源**。省的是每次的计算和显存带宽（参数仍要存，专家并行的显存占用不变）。

**三个工程魔鬼**：

1. **负载不均（Load Imbalance）**：Router 自由学习会塌缩——大家都挤进少数"明星专家"，其他专家饿死，集群里大部分卡闲置。解法：辅助负载均衡损失（惩罚路由分布的偏斜）+ capacity factor（给每个专家设缓冲区，超了就丢 token）。**DeepSeek 的改进（noaux routing + shared expert）**：不用 aux loss（因为它干扰语言损失），改在打分里加 bias 项做均衡，另设"共享专家"承载通用知识，让路由专家专注专门化。
2. **All-to-All 通信**：专家并行（Expert Parallelism）下，token 要跨卡找到自己的专家——每层一次全交换，带宽需求极高（《五道坎》第二章的"通信地狱"）。通信和计算的 overlap 设计决定集群效率。
3. **训练不稳定**：稀疏路由的梯度只流向被选中的专家，且路由决策不可微（top-k 离散）。细粒度专家（很多小专家 vs 少量大专家）+ 更高的路由自由度是 DeepSeekMoE 的另一个贡献。

## 三、为什么 MoE 是"性价比怪兽"

给定算力预算 FLOPs，MoE 的损失曲线显著优于稠密（同样的训练计算，总参大几倍）。代价转移到**显存和系统**：参数多了，存和通信变贵。所以 MoE 的兴衰和硬件强相关——**在互联便宜的集群上 MoE 大胜，在单卡上稠密反而香**。这就是为什么 MoE 的工业化（Switch → GLaM → Mixtral → DeepSeek-V3）伴随着集群互联的进步。

## 四、边界

1. **显存没有省**：MoE 省计算不省存储，部署门槛依然高——量化 + 专家卸载（offloading 冷专家）是补丁。
2. **专家不等于"可解释的学科专家"**：路由学到的是统计分工，不是"这个专家管数学"，可解释性仍是黑盒。
3. **微调比稠密娇气**：路由在分布漂移下容易失衡（微调后专家负载重新洗牌），需要小心处理。

## 五、记忆卡

| 概念 | 一句话 |
|------|--------|
| MoE | FFN 换成 N 选 k 的专家池，容量与计算解耦 |
| Router | 每 token 打分挑 top-k 专家，权重加权输出 |
| 负载均衡 | 防止路由塌缩：aux loss 或 DeepSeek 的 bias 方案 |
| 专家并行 | 专家放不同卡，代价是每层 All-to-All |
| 共享专家 | 承载通用知识，路由专家只管专门化 |
| 代价 | 省计算不省显存；通信地狱；微调娇气 |

一句话总结：**MoE 不是新算法，是一笔交易——用系统复杂度（通信、均衡、显存）换同算力下更大的知识容量。集群越强，这笔交易越划算。**
