# 07 · 推理引擎解剖：vLLM 凭什么把吞吐翻了 20 多倍

## 一句话

vLLM 的两板斧——**PagedAttention + Continuous Batching**——没有发明任何新模型，只是把操作系统五十岁的两件老手艺（虚拟内存分页、任务调度）搬进了 KV Cache 管理。LLM 推理的系统工程史，就是一部"OS 概念重演史"。

---

## 一、先看旧世界浪费在哪（2023 年之前）

自回归生成每步都要用历史 token 的 Key/Value——KV Cache。早期推理框架（FasterTransformer 等）按**最长可能序列**预分配连续显存：

- 一个"最长 2048"的槽位，请求实际只用了 200 token → **90% 的显存空转**；
- 显存碎片（内部碎片 + 外部碎片）导致新请求挤不进来；
- 批处理是静态的：这一批里最慢的请求没跑完，所有卡都陪它等（一个长请求拖着全队）。

实测 KV Cache 有效利用率经常只有 20-40%。**GPU 在"算力过剩、显存被浪费"的状态下打转**——这正是《五道坎》显存墙的工程版。

## 二、板斧一：PagedAttention——给 KV Cache 装上虚拟内存

借 OS 的分页思想：把每个请求的 KV Cache 切成固定大小的**块（block，如 16 个 token 一块）**，维护一张页表（block table）记录逻辑位置 → 物理块的映射：

1. **按需分配**：用到多少分多少块，不再按最长序列预分配——浪费率从 60-80% 压到 4% 以下；
2. **块可以不连续**：物理显存随便散落，逻辑上连续——外部碎片消失；
3. **前缀共享**：多个请求共享同一系统提示词的 KV，**物理块直接共享**（引用计数管理）——相同前缀只存一份，批间节省可达数倍；
4. **写时复制（Copy-on-Write）**：共享前缀的请求分叉后，只有分叉处的新块才复制——OS 的 COW 原样照搬。

代价：访存不连续 + 页表查找，需要重写注意力 kernel（gather 式访问块）。这是 vLLM 论文的真正工作量：**kernel 为分页重写，而不是算法上的新东西**。

## 三、板斧二：Continuous Batching——调度器从"批"细化到"步"

旧方式（static batching）：凑一批请求一起跑，全批结束才收下一批——短板请求陪长板坐牢。

Continuous batching：**调度粒度从"批"细化到"单步"**。每一步 decode 后检查：谁完成了，立刻从批里摘除、把它的槽位让给新请求；prefill 阶段的请求也按预算插入。GPU 的 batch 槽位永远满载。

类比：餐馆从"一桌客人全部吃完才翻台"改成"谁吃完谁走、空位立刻上新人"。Orca（OSDI'22）首创迭代级调度，vLLM 把它和分页拼起来成为标配。

## 四、后续拆解：现代推理引擎全景

vLLM 之后，推理系统沿着同一张地图继续推进：

| 技术 | 解决什么 | 一句话原理 |
|------|----------|-----------|
| Chunked Prefill | 长 prompt 阻塞 decode | 把 prefill 切块，和 decode 混跑，压 TPOT 毛刺 |
| Prefix Cache / RadixAttention | 公共前缀重复计算 | 前缀 KV 建成基数树，全局复用 |
| Speculative Decoding | decode 受带宽限制 | 小模型起草、大模型并行验证，一步出多 token |
| PD 分离（DistServe/Mooncake） | prefill 和 decode 互相干扰 | 两阶段拆到不同实例，KV 跨机迁移 |
| 量化 KV / FP8 | KV 吃显存 | 压 KV 精度换容量带宽 |
| 分层 KV（Mooncake） | 长上下文 KV 爆炸 | 热 KV 在 HBM、冷 KV 下沉主存/远端 |

**共同规律一句话：所有优化都在回答同一个问题——"在带宽限死的 decode 里，怎么让一次权重/KV 读取多产出 token"。**

## 五、OS 概念重演史（这篇的真正论点）

| 操作系统 | 推理引擎 |
|----------|----------|
| 虚拟内存分页 | PagedAttention |
| 页表 | Block Table |
| 写时复制 COW | 前缀分叉 |
| 进程调度 | Continuous Batching |
| 多级存储（RAM/磁盘） | KV 分层（HBM/主存） |
| 缓存 | Prefix Cache / Radix Tree |
| 内存交换 swap | KV offloading |

这不是巧合：**两个系统都在做同一件事——管理"远大于物理容量的并发工作集"。**OS 用五十年踩出来的坑，LLM 推理正在加速重踩一遍。做推理系统的人最该读的书不是新论文，是操作系统教科书。

## 六、判断

1. 引擎层的竞争已经从"单点技术"转向"系统完成度"（vLLM 通用、SGLang 结构化生成、TRT-LLM 极限性能），护城河是工程生态不是论文。
2. 下一个重演的 OS 概念大概率是**更完整的虚拟化**：跨机 KV 的统一编址与迁移——Mooncake 已经在路上了。
3. 给求职者的提示：这个领域要的是"懂 OS + 懂 GPU + 懂模型"三合一的人，恰好是 AI Infra 路线第一、三层的内容。

一句话总结：**vLLM 的 20 倍吞吐不是模型突破，是把 1960 年代发明的虚拟内存搬到 2023 年的 GPU 上。系统工程的复利，比算法炼丹可靠得多。**
