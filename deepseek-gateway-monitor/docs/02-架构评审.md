## 1) 架构门禁（Gate Decision）
**结论：有条件放行（Conditional Pass）。** PRD 在硬约束（纯只读、标准库、`192.168.112.252:8080` 不可改）与 Out-of-Scope 上做得扎实，可测性高。但存在 3 项必须修订后方可交付：

- **R1（必改）**：补充 `--header` 可配置项。网关为反代，可能要求 `Authorization: Bearer` 或自定义 `X-*` 头，否则 `/v1/models`、`/health` 直接 401，健康检查与压测全部误判失败。
- **R2（必改）**：补充 `--mock` 离线模式。沙箱/无 Tailscale 时无法直连内网网关，必须能用内置样例数据跑通 check/bench/report，保证演示与 CI 不依赖网络。
- **R3（建议）**：退出码与错误分级在 PRD §3 已有雏形，但需补「部分失败」语义——压测中成功率 <100% 但非全失败时，应退出 `0` 并标注降级，而非笼统 `1`；另补 `--json` 机器可读输出，便于后续接入校验。

## 2) 架构设计

### 2.1 单文件 vs 多文件 CLI
- **决策：单文件 `monitor.py` + `python -m monitor` 入口**。
- 理由：三子命令共享同一套 `urllib` 探测/超时/退出码逻辑，代码量预计 400~600 行，单文件内聚反而更利于纯标准库零依赖分发；多文件包结构（setup.py/__main__）收益不抵复杂度。
- 结构建议（单文件内分区，非多文件）：`argparse` 子命令解析 → `probe()` 通用探测函数 → `cmd_check/cmd_bench/cmd_report` → 统一 `exit(code)`。公共逻辑抽 2~3 个内部函数（`http_get`、`measure_latency`、`quantile`）即可，不引入类层次。

### 2.2 HTTP 探测（urllib 实现要点）
- 统一用 `urllib.request.Request(method="GET", url, headers=...)`，强制 `method="GET"` 杜绝误用写方法。
- `urllib.request.urlopen(req, timeout=...)` 包在 `try/except` 中，分别捕获 `urllib.error.URLError`（网络/DNS/超时）、`HTTPError`（非 2xx）、`socket.timeout`；**绝不裸 raise 到顶层**。
- 只读护栏：构造 Request 时拒绝任何 `data=` 参数；`bench` 的 echo 路径需 `--allow-echo` 显式开启，且仅接受最小 payload 白名单。
- 重定向：默认跟随，但 `urlopen` 对跨域重定向有安全限制，保持默认即可（只读 GET 无副作用）。

### 2.3 压测并发模型（threading + 限流，避免打垮 192.168.112.252:8080）
- 模型：`concurrent.futures.ThreadPoolExecutor(max_workers=concurrency)` 驱动 N 个 worker 线程，每个线程循环领取「待发请求」直至总数耗尽（worker 数 = concurrency，任务数 = requests）。
- 限流护栏：用 `threading.Semaphore(concurrency)` 硬控并发上限（默认 4，封顶 16）；**不**用无界线程池。可选 `--rate`（req/s）令牌桶（基于 `time.sleep` 简单节流）防突发，默认不限速但 concurrency 已兜底。
- 计数：`--requests` 默认 100；超限必须显式传参；`--dry-run` 仅打印计划（worker 数 / 总请求 / 目标端点）不发请求。
- 安全：仅打 `/health`、`/v1/models` 等只读端点；echo 路径（`/v1/chat/completions` + `stream:false` + 最小 prompt）默认关闭且需 `--allow-echo`。

### 2.4 延迟测量与 p 分位算法
- 测量：每次请求用 `t0 = time.perf_counter()` 包裹 `urlopen`，`latency_ms = (t1-t0)*1000`，仅记录成功请求；记录每个样本的 `{ok, latency_ms, ts, status}`。
- p 分位：对成功样本延迟升序排序后**最近秩法**（nearest-rank）：`idx = ceil(p/100 * n) - 1`，取 `sorted[idx]`。P50/P95/P99 直接套用，避免引入 `statistics` 之外的依赖（排序+取位足够、确定性好、易测）。
- 吞吐：`throughput = 成功数 / 总耗时(wall-clock)`；成功率 `= 成功数 / 总请求数`。

### 2.5 token 用量接口探测策略
- 先探：`OPTIONS` / `GET /v1/usage`（或探测响应头 `x-total-tokens`、`x-prompt-tokens`）；用 `cmd_check` 同款只读 GET，带 `--header` 鉴权。
- 判定：返回 2xx 且含数值 → 取真实值并标注「真实（来源 /v1/usage）」。
- 失败降级：401/404/超时 → 进入估算分支：`估算 token = 请求数 × 平均单次 token（压测样本或经验常数）`，输出必须含醒目「**估算**」字样及来源说明。
- `--from-bench`：复用最近压测样本（落本地临时 JSON）做估算，避免二次探测。

### 2.6 退出码与错误分级
统一在 `main()` 末尾 `sys.exit(code)`：
- `0` 成功（check OK / bench 完成 / report 生成；含成功率<100% 的降级完成）。
- `1` 业务不可用（check 全失败、bench 全失败、usage 真实源与估算均不可得）。
- `2` 参数/用法错误（argparse 自动抛出）。
- `3` 致命异常（网络外未预期错误，须 `try/except Exception` 捕获后退出，禁止栈溢出到终端）。
- 错误分级：网络层（URLError/timeout）→ 标记为 `UNREACHABLE` 仍走 `1`，不抛未捕获；HTTP 层（4xx/5xx）→ 区分 `401 AUTH`（提示 `--header`）与 `5xx GATEWAY`；分级信息写入报告「错误分级」段。

## 3) 风险与缓解

| 风险 | 影响 | 缓解（已纳入架构） |
|---|---|---|
| 网关为反代，需 `Bearer`/自定义 header | 探测全 401，误判不可达 | **R1**：`--header "Authorization: Bearer ..."` 可配，默认空；401 时提示加 `--header` |
| 沙箱无 Tailscale，连不上 `192.168.112.252:8080` | 无法演示/CI 必败 | **R2**：`--mock` 返回内置样例（健康 OK+延迟、压测 p 分位、估算日报），全链路离线可跑 |
| 压测误伤真实业务流量 | 网关 5xx 风暴 | concurrency≤16 信号量 + 默认 4；仅只读端点；`--dry-run` 预检 |
| 用量接口不存在/不稳定 | 日报无数据 | OPTIONS/GET 探活失败即降级估算，强制标注「估算」 |
| 未捕获异常暴露栈 | 退出码不可控、体验差 | 全局 `try/except` 兜底 → 退出码 `3` |

> 交付前置条件：R1、R2 必须合入 PRD 修订；R3 建议合入。修订后 dev 方可开工。
